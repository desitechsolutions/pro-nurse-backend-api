# Security Policy - Pro Nurse Engine

This document outlines the security policies, handling of sensitive data, and reporting standards for the **Pro Nurse Platform**, maintained by the engineering team at **Biruma Technology Solutions Pvt Ltd.**

---

## 1. Vulnerability Disclosure Process

If you discover a security vulnerability in this project, **please do not open a public issue.** Instead, follow our responsible disclosure process:

1. Send an email with a detailed description of the vulnerability, replication steps, and the affected version to: [info@desitechsolutions.com](mailto:info@desitechsolutions.com).
2. The security response team will acknowledge receipt of the report within 24 hours.
3. A fix will be developed, tested, and deployed to staging.
4. We will coordinate a rollout and announce updates in our private release logs.

---

## 2. Cryptographic Secret Management

1. **Credentials Separation:** All database usernames/passwords, external service secret keys (Razorpay key secret, FCM credential files), and JWT sign keys must never be saved in code.
2. **Environment Configuration:** Deployments must use platform-level environment variables:
   - `DATABASE_URL`
   - `DATABASE_USERNAME`
   - `DATABASE_PASSWORD`
   - `JWT_SECRET`
   - `RAZORPAY_KEY_ID`
   - `RAZORPAY_KEY_SECRET`
   - `FIREBASE_CREDENTIALS_PATH`
3. **Local Development Exclusion:** Developers must configure secrets inside local property files which are explicitly untracked via local ignore files.

---

## 3. JWT Security & Expiry Controls

1. **Short-Lived Access Tokens:** Access tokens issued by `/api/auth/otp/verify` must have a short lifespan (e.g. 1 day maximum for local testing, 1 hour or less for production).
2. **Secure Refresh Tokens:** Refresh tokens must be set inside HttpOnly, Secure, and SameSite=Strict cookies. This prevents cross-site scripting (XSS) attacks from accessing or extracting the token.
3. **Rotation:** Refresh tokens are rotated automatically on every `/api/auth/refresh` request. When a new access token is requested, the old refresh token is invalidated, and a new one is set in the secure cookie context.

---

## 4. Sensitive Logging Restrictions

1. **Masking OTPs:** Never log raw OTPs generated by `/api/auth/otp/send` in console output or log files.
2. **Masking Access Tokens:** JWT access and refresh token strings must be filtered and replaced with placeholders in log statements.
3. **GDPR/PII Data Compliance:** Personal identification numbers (e.g., patient phone numbers, chronic illness profiles, and addresses) must not be written to info-level application logs.

---

## 5. Dependency Vulnerability Management

1. The project uses Flyway database migrations and Spring Security to enforce state sanity.
2. Run vulnerability scans regularly:
   ```bash
   mvn dependency-check:check
   ```
3. Update outdated dependencies in `pom.xml` promptly.

---

## 6. Developer Security Checklist

Ensure the following are checked before pushing code:
- [ ] No hardcoded passwords, tokens, or credentials are added to Java files.
- [ ] No raw SQL concatenations are used (to prevent SQL injection). Rely on JPA query parameters.
- [ ] Input validation is applied using `@Valid`, `@NotBlank`, `@NotNull`, etc., on all incoming DTO requests in controllers.
- [ ] Role constraints are enforced using `@PreAuthorize("hasRole('...')")` on all protected controller methods.
